### 1.6 幂等与防重复执行

| # | 用例 | 方法 | 预期 | 状态 |
|---|------|------|------|------|
| 1.6.1 | Webhook 同 fingerprint 重发 | 同 alertname+instance+severity 连发 4 次 | 仅首次触发分析，后三次被 Redis SETNX 挡掉 | ✅ |
| 1.6.2 | 同 taskId 重复提交 | 连发两次 `/api/agent/start` 同 taskId | 第二次 **409** | ✅（单测覆盖） |
| 1.6.3 | 任务终态不回退 | 任务 SUCCESS 后重发同 taskId | 状态保持终态 | ⬜ |

```bash
# 1.6.1 实测脚本（连发 4 次同 fingerprint）
T=$(curl -s -X POST http://localhost:8081/api/auth/login -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}' | python -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")
before=$(curl -s -H "Authorization: Bearer $T" "http://localhost:8081/api/tasks?page=1&size=1" | python -c "import sys,json;print(json.load(sys.stdin)['data']['total'])")
B='{"version":"4","status":"firing","receiver":"aiops","alerts":[{"status":"firing","labels":{"alertname":"IdemStrictProbe","severity":"critical","service":"idem-strict","instance":"10.99.88.77","namespace":"default"},"annotations":{"summary":"IdemStrictSummary","description":"idem strict probe"},"startsAt":"2026-09-23T18:10:00Z"}]}'
for i in 1 2 3 4; do curl -s -o /dev/null -w "第${i}次 %{http_code}\n" -X POST http://localhost:8081/api/alerts/webhook \
  -H "Content-Type: application/json" -H "X-Webhook-Token: dev-webhook-token" -d "$B"; done
sleep 8
after=$(curl -s -H "Authorization: Bearer $T" "http://localhost:8081/api/tasks?page=1&size=1" | python -c "import sys,json;print(json.load(sys.stdin)['data']['total'])")
echo "任务增量 $((after-before))（期望 1）"
```

**实测结果（2026-09-23）**：4 次全部 202；**任务增量 = 1**，**告警落库 = 1 条** ✅ 幂等防线有效。

### 5.2 审批闭环（manual 模式，高危操作 → 人工介入）

**关键**：审批必须经 WebSocket 广播到前端，且前端 WS 必须常驻——否则必然 55s 超时。

| 步骤 | 操作 | 预期 | 状态 |
|------|------|------|------|
| 1 | 确认 `opsagent.approval.mode: manual` | application.yml 为 manual | ✅ |
| 2 | 触发一次高危操作（回滚/大比例扩容） | Agent 调用 `request_human_approval` | ✅ |
| 3 | 审批单落 Redis + MySQL | `/api/approvals?status=PENDING` 可见新单 | ✅ |
| 4 | 前端收到推送 | 审批页实时出现待办（**不加轮询**） | ✅ |
| 5a | 55s 内批准 | `POST .../decision {"approved":true}` → Agent 继续执行 | ⬜ |
| 5b | 55s 内拒绝 | Agent 收到 rejected，走稳妥路径，**不执行高危动作** | ⬜ |
| 5c | 55s 超时 | fail-closed：`mode=timeout`，`approved=false`，**不执行** | ✅ |
| 6 | 切 `mode: auto` 复测 | 立即批准，但落审计记录（requestId 可查） | ⬜ |

**5c 实测结果（2026-09-23，全程不中断等待 55s）** ✅：

```
工具返回 HTTP 200
  success=True                       ← 请求送达成功
  approved=False  mode=timeout       ← 但没批准
  message=Approval timed out after 55s (...): rollback nginx —
          proceed with the safe alternative, do NOT execute the high-risk operation.
落库: status=TIMEOUT  decidedBy=system  note=Waiting approval timed out
```

> 关键点：`success=true` 与 `approved=false` **刻意分离** —— 前者是「请求送达」，
> 后者才是「批没批」。混在一起 Python 侧就分不清「审批被拒」和「审批服务挂了」。
> 且提示词明确指示 **do NOT execute the high-risk operation**，fail-closed 语义完整。

**4 实测结果**：不停在任何任务页（不带 taskId 连 WS）也能收到
`{"type":"APPROVAL_PENDING",...,"timeout=55"}` 广播 —— 广播防线有效。

> 超时上限 55s 必须 **小于** Python 侧 `HTTP_READ_TIMEOUT`（60s），否则审批没结束 Python 先超时。

### 9.1 修复实现（已完成）

`Alert` 类加字段别名，**不改落库字段名**，两套写法都能读：

```java
@JsonIgnoreProperties(ignoreUnknown = true)   // Alertmanager 版本升级会加字段，不能因此丢告警
public class Alert {
    @JsonAlias({"level"})            private String severity;
    @JsonAlias({"message","summary"}) private String title;
    @JsonAlias({"msg"})              private String description;
    @JsonAlias({"service","svc"})    private String serviceName;
    ...
}
```

> 注意**不能**用 `@JsonIgnoreProperties(ignoreUnknown = false)` 严格拒绝未知字段：
> Kafka 消费（`AlertIngestionService.consumeAlert`）复用同一个 `Alert` 类，
> 上游监控系统加任何字段都会导致整条告警被丢弃——那比"字段名写错"严重得多。
> 所以选择**兼容别名**而非严格校验。

### 9.6 修复实现（已完成）

- `GlobalExceptionHandler` 全部改为返回 `ResponseEntity`，把业务 code 映射成真实 HTTP 状态码
  （新增 `BusinessException` 独立处理，按 code 映射 400/404/409）。
- `AuthController.login` 返回真实 **401**（同时把"用户不存在"与"密码错误"统一为同一条 message，**避免账号枚举**）。
- `TaskController.getTask` 返回真实 **404**。
- `ApprovalController.decide` 返回真实 **400**。
- 新增 `ServerWebInputException` 处理，把 JSON 格式错误从 500 纠正为 **400** 并带上根因
  （注意捕获的是 `ServerWebInputException` 而非 `DecodingException`——WebFlux 会层层包装，
  直接捕获内层匹配不到，会漏成 500）。
- 前端 `request.js` 补两处：① 非 2xx 时优先展示后端 body 里的中文 message（原先只显示 axios 的英文）；
  ② 登录接口的 401 不触发登出跳转（否则用户在登录页输错密码会被强行刷新）。

**刻意的例外**：`/api/tools/execute` 与 `/api/agent/callback/tool` 对「工具执行失败」**始终返回 HTTP 200**，
成败由 body 的 `data.success` 表达。若映射成非 2xx，Python agent 的 `raise_for_status()`
会在异常分支丢掉结构化的失败信息，Agent 就无法如实告诉 LLM「重启失败了、原因是什么」。
