## 5.1 LLM 服务限流影响

- 多次触发的 `leaky-app` 分析会打满 DashScope qwen-turbo 的请求限流，
  表现为 `429 Too Many Requests`。
- 受影响的是辅助通道：Query 润色、Reflection、Rerank。
  Rerank 失败已有 RRF 降级；Query 润色失败已有原句降级；Reflection 失败默认放行。
- 本次优化：`query_rewriter.py` / `reflection.py` 的 `ChatOpenAI`
  显式设置 `timeout=15s, max_retries=1`，避免辅助通道在高限流下反复指数退避重试，
  把主 Agent 拖慢。主链路 `DeepSeek` 调用不受影响。
- **注意**：该优化写入时间为 2026-10-17 16:54，若 Python 5000 进程启动早于该时间，
  需要重启 Python 5000 才生效。
- 审批修复（Supervisor current_subtask）写入时间为 18:04-18:05；
  当前 Python 5000 启动于 17:43，需再次重启 Python 才能一并加载。
  重启命令：先停 5000，再 `cd D:/桌面/智能运维项目/aiops-agent && .venv/Scripts/python.exe main.py`。

## 5.2 审批挂起不是“卡死”

- manual 模式下，执行 Agent 只要决定做写操作，就会创建 PENDING 审批单并
  `interrupt()` 挂起 LangGraph。任务状态会保持 RUNNING，直到人工批准/拒绝
  并通过 `/api/agent/resume` 恢复。
- 本次实测发现审批单 operation 一度显示“未知高危操作”，原因是 Supervisor
  未把 `current_subtask` 写入状态。已修复：
  - `supervisor.py`：路由 executor 时写入 `current_subtask`，并根据根因生成可读审批名
    （重启故障服务 / 处理内存资源 / 回滚服务版本 / 调整副本数 / 恢复服务可用性）。
  - `executor.py`、`graph.py`：默认 operation 从“未知高危操作”改为明确文案。
- 前端应把 RUNNING + PENDING 审批理解为“等待人工处理”，不能判定为链路卡死。
- 进一步修复：即使提示词明确“只读诊断、不要修复”，健康 nginx 仍会因根因文本
  含“重启/异常”等词被路由到执行/审批。现在 `_needs_repair` 必须同时满足
  `_evidence_indicates_failure`（真实证据显示 degraded/断流/CrashLoop 等），
  健康服务不再产生审批单。该修复写于 2026-10-17 18:15，也需要重启 Python 生效。
